# Git 和 GitHub 团队协作规则

来源：`Trae_Git_GitHub_团队协作管理规则.docx`，这里整理成我在仓库里日常可执行的中文版本。

## 核心原则

- 不直接在 `main` 或 `master` 上开发。
- 每个功能、整理任务或修复都放在独立分支。
- 测试或检查不通过，不合并。
- 每次提交只做一件事，提交说明要能看懂。
- 重要改动需要先看是否符合需求，再看代码或内容质量。

## 分支命名

- 新功能：`feature/简短描述`
- 修复问题：`fix/简短描述`
- 实验尝试：`experiment/简短描述`

如果中文分支名在本地 Git 环境里创建失败，可以用拼音或英文分支名，但仓库内的目录、文件名和说明继续使用中文。

## Worktree 隔离

团队规则要求用 worktree 做隔离开发时，目录不能被 Git 跟踪。

本仓库已经在 `.gitignore` 中忽略：

```text
.worktrees/
worktrees/
```

创建 worktree 前先确认这两个目录仍在忽略清单里。

## 推荐工作流

1. 明确要做什么，以及这次改动算教学、运营、工具还是协作规则。
2. 新建独立分支。
3. 修改文件并自查敏感信息。
4. 运行必要检查，例如查看网页工具能否打开、说明链接是否正确。
5. 提交到分支。
6. 推送到 GitHub。
7. 创建 Pull Request。
8. 合并前完成内容检查和质量检查。

## Pull Request 模板

```markdown
## 变更内容
- 

## 测试情况
- [ ] 中文目录和说明可读
- [ ] 没有提交 token、账号、学生家长隐私或业务原始数据
- [ ] 网页工具入口仍能打开
- [ ] worktree 目录没有被提交

## 关联事项
- 
```

## 代码审查和内容审查

每次重要改动至少看两遍：

- 规格合规审查：这次整理是否符合目标和团队规则。
- 质量审查：文件是否清楚、链接是否正确、有没有隐私或安全风险。

收到反馈时不要只说“收到”。需要判断反馈是否正确、为什么要改、怎么验证。

## 红线

- 不把 token、密钥、账号密码放进仓库。
- 不上传真实学生、家长、老师的隐私信息。
- 不把飞书、表格、导出文件里的原始业务数据直接提交。
- 不在测试失败或检查失败时强行合并。
- 不为了省事跳过 Pull Request。
